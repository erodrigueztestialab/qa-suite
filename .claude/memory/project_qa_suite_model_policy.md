In TestIALab QA Suite (`C:\TestiAlab\QA-Suite\proxy.js`), the STRONG model tier is reserved ONLY for the 3 M4 (Escenarios y Casos QA) endpoints: `/api/generate-cases`, `/api/generate-gap-cases`, `/api/verify-coverage` (all three call with `callOpts = { engine: engine, model: 'opus' }`, unconditional on engine). Every other endpoint must use the standard tier — `/api/analyze` (M1), `/api/generate-plan` (M3 Plan de Pruebas), `/api/generate-certification`, `/api/estimate-complexity` (M2), `/api/verify-evidence` (M5), `/api/chat-qa`.

**This is dual-engine, not Claude-only** (corrected 2026-09-08 — see [[project_qa_suite_status]] Sesion 10): `model:'opus'` is the generic `opts.model` key `callAI`/`callClaude`/`callGemini` all share — for `engine==='claude'` it selects real Opus; for `engine==='gemini'` it maps through `GEMINI_MODEL_MAP.opus = 'gemini-3.1-pro-high'` instead of the default `GEMINI_MODEL_MAP.sonnet = 'gemini-3.1-pro-low'`. Passing `model:'opus'` unconditionally in the 3 M4 endpoints is what makes both engines get their own "strong" tier.

**Why:** User corrected this explicitly on 2026-08-19: "Oppus SOLAMENTE es para la generación de casos, todo lo demás lo haces con sonnet medio" — after noticing M1's `/api/analyze` and M3's `/api/generate-plan` were also hardcoded to `model:'opus'` (left over from earlier iterations), making those calls needlessly slow. Case generation is the one task the user considers critical/complex enough to justify the strong tier's extra cost and latency (100% coverage of CA/RN, no redundancy between cases). **Extended 2026-09-08:** when Gemini/Antigravity was added as a second engine (2026-08-26), this policy was never carried over to it — all 3 M4 endpoints had `engine === 'claude' ? {model:'opus'} : {engine}`, so Gemini silently ran M4 on its WEAK model (`-low`) the entire time. Found while debugging a user report of M4 generating too few cases; fixed by making all 3 unconditional. See [[feedback_check_all_edges]] for the general lesson (grep for every copy of a pattern, not just the reported one).

**How to apply:** Before adding or touching any `callAI(...)` call in `proxy.js`, check which endpoint it's in. If it's one of the 3 M4 endpoints above, pass `model:'opus'` UNCONDITIONALLY (both engines). If it's not, it must pass `model:'sonnet'` (or omit `model` entirely, defaults to standard tier for both engines). Don't reintroduce the strong tier elsewhere without the user explicitly asking again, and don't let a new engine branch skip the tier a policy already applies to another engine.

**Effort flag added 2026-09-16 (M1/M2/M3 only so far):** the user's original 2026-08-19 wording was literally "sonnet **medio**", but no `--effort` flag existed in the Claude CLI back then, so "medio" was never actually enforced — it was just whatever the CLI defaulted to when no effort flag was passed. The CLI (confirmed v2.1.270) now exposes a real `--effort <level>` flag (`low|medium|high|xhigh|max`). `callClaude()` in `proxy.js` now accepts `opts.effort` and forwards it as `--effort <level>` (separate from the older `opts.thinking==='high'` ultrathink hack, which still exists unused). At the user's explicit request, `/api/analyze` (M1), `/api/estimate-complexity` (M2) and `/api/generate-plan` (M3) now pass `effort:'medium'` explicitly alongside `model:'sonnet'`. Verified for real: `claude --effort medium --model sonnet` accepted the flag with no error (rc=0, real response). **Not yet extended to Gemini** (no known equivalent concept confirmed) nor to the other standard-tier endpoints (`/api/generate-certification`, `/api/verify-evidence`, `/api/chat-qa`) nor to M4's Opus calls — the user only asked for M1/M2/M3 this round; if they later want "medio" locked in everywhere standard-tier applies, or an equivalent for M4/Gemini, extend the same pattern (grep `callAI(` for every site missing `effort:`, per [[feedback_check_all_edges]]).
